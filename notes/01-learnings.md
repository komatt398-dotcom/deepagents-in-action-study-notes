# 学习心得：八条认知与三次被证伪的直觉

> 目标不是记住 API，而是形成一套能迁移到其他 Agent 框架的判断标准。

## 1. 能力分四层

一开始以为把讲义里的工具抄进 `tools=[]` 就算集成完了。真正做下来才发现，16 章在讲同一件事的四个层面：

| 层面 | 典型章节 | 本质问题 | 失败表现 |
| --- | --- | --- | --- |
| 上下文 | 虚拟文件系统、技能、长期记忆 | Agent 该看到什么，存在哪 | 新线程失忆、prompt 越写越长 |
| 控制流 | Todo、子 Agent、异步子 Agent、动态子 Agent | 谁来做、同步还是异步、怎么分工 | 主线程被长任务堵死、委派后拿不到材料 |
| 安全边界 | 人工审批、文件权限 | 哪些动作必须问人，哪些路径不许写 | 模型"答应"不改文件，实际照改 |
| 质量闭环 | 评分量表、流式可观测 | 怎么证明做对了 | todo 全绿但报告没有依据 |

把这四层补齐之后，Agent 的行为才从"随机发挥"变成"可预期"。

## 2. 上下文工程是存储问题，不是 prompt 问题

最有效的三个改动都没改 prompt：

- **后端路由**：把线程态、跨线程记忆、只读参考分到不同后端。同一条 `/skills/` 路径，读是真文件，写直接拒绝。
- **记忆分层**：`/memories/` 用持久 Store，新线程仍能读到；种子写入幂等，避免每次启动覆盖用户已学到的偏好。
- **技能渐进披露**：`SKILL.md` 只在系统提示里放索引，需要时再读全文。

一个具体收益：把两份技能规范从 system prompt 移到 `/skills/` 后，提示词长度明显下降，而且改技能不用改代码。

## 3. 记忆要克制

反直觉的点：**记忆不是越多越好**。

把"当前任务细节"写进长期记忆，下次开新线程会污染判断。课程里"什么不该记"的清单比"什么该记"更有价值：

- 不记：临时状态、一次性任务、寒暄、密钥。
- 记：稳定的用户偏好、角色设定、被纠正过的错误模式、工具使用约定。

判断标准可以简化成一句：**这条信息在下一次无关任务里，还会影响决策吗？**

## 4. 安全必须在工具层

最初的方案是在 system prompt 里写"不要修改 `/skills/`"。实测发现，模型心情好会遵守，心情不好照样写。

改成声明式权限后才真正生效：

```python
FilesystemPermission(operations=["write"], paths=["/skills/**"], mode="deny")
FilesystemPermission(operations=["write"], paths=["/secrets/**"], mode="interrupt")
```

审批同理：把发布报告、发送邮件注册成需要人工确认的动作，运行到那里就停住。

> "模型承诺不做什么"不是安全机制，"运行时不让它做"才是。

## 5. 子 Agent 的上下文隔离是双刃剑

派出去的 research-agent 拿不到主线程的对话历史。

- 好处：上下文干净，不会被无关消息干扰。
- 坏处：你只说"研究附件里的内容"，它根本不知道附件是什么。

课程里有一句很关键：**新线程没有旧消息 ≠ 历史被删除**。正确做法是先把材料落到共享文件，再在委派描述里明确让它去读。

## 6. 可测试性是分水岭

这套代码能持续改得动，根本原因是测试只脚本化**模型**：

```python
ScriptedModel(replies=[
    call("write_todos", {"todos": [...]}, "plan"),
    AIMessage(content="Checked."),
])
```

图、工具、文件系统、检查点全是真的。这样验证的是机制，而不是"模型这次回答得好不好"：

| 测试 | 断言 |
| --- | --- |
| 权限 | 模型故意写 `/skills/x/SKILL.md` → tool 返回 permission denied |
| 审批 | 模型调用 `publish_report` → 状态出现 `__interrupt__` |
| 记忆 | 直接查 store，内容落盘且重复种子不覆盖 |
| 技能 | 系统提示里出现技能索引与记忆正文 |
| API | 流式事件中的 `todos` 状态最终为 completed |

11 个测试约 90 秒跑完，不需要任何 API key。没有这层测试，改 middleware 顺序就是盲改。

## 7. 版本漂移是最大的隐性成本

讲义部分章节基于 0.7.10 / 0.7.15，模板锁的是 0.7.8。结果：

- `CodeInterpreterMiddleware`（解释器 / 动态子 Agent）在 0.7.8 里根本不存在。
- 一些新参数只能靠 `inspect.signature` 逐个确认。

最后的处理是"能落的落地，落不了的降级为开关 + 明确告警"，而不是硬写一个 import 就炸的代码。

**先冻结版本，再按版本核 API，比照着讲义抄更省时间。**

## 8. 对厂商案例保持证据分级

课程提到 Cursor 用 Turbopuffer 降本 20 倍。机制是真的，但数字来自厂商案例，且成立前提很窄。详见 [案例评析](04-case-review-turbopuffer.md)。

结论：**机制可信 ≠ 数字可信 ≠ 适用于你的场景。** 写报告时至少标注"厂商披露"，而不是当成行业定论。

## 三次被证伪的直觉

### 直觉一："工具越多，Agent 越强"

错。工具数量上升后，模型选错工具的概率也上升。更有效的做法是**减少重叠工具 + 在描述里写清边界**。技能（按需加载）比工具（常驻）更适合承载"流程知识"。

### 直觉二："在 prompt 里写清楚规则就够了"

错。规则分两类：

- **偏好类**（语气、结构、引用格式）→ prompt 有效。
- **约束类**（不许写某目录、发布前必须审批）→ 必须落到运行时。

把约束类写进 prompt，只会得到"看起来遵守"的假象。

### 直觉三："测试要测最终答案"

错。模型输出不确定，测最终答案会得到一堆脆弱的断言。正确做法是测**机制**：某个工具被调用了吗？状态字段变了吗？权限拦截生效了吗？

## 迁移到其他框架时，我会先问的五个问题

1. 上下文存在哪？线程态、跨线程、只读参考是否分离？
2. 子 Agent 的上下文是否隔离？隔离后材料怎么传？
3. 有没有工具级权限，而不只是 prompt 约束？
4. 能不能在没有模型密钥的情况下验证机制？
5. 版本升级时，哪些 API 是"讲义有、当前版本没有"的？
